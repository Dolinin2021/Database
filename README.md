# Практическое задание с самопроверкой «Базы данных, их типы»

## Задание 1. СУБД

1.1. Бюджетирование, финансовая отчётность и прогнозирование рисков

• **Рекомендуемый тип СУБД:** Реляционная СУБД (SQL) для транзакций и учёта + Колоночная СУБД (OLAP) для аналитики и прогнозирования. *Примеры:* PostgreSQL в связке с ClickHouse или Greenplum. \
• **Почему:** Финансовые данные требуют строгой типизации, чёткой схемы (счета, статьи расходов, договоры) и соответствия стандартам ACID (гарантия целостности транзакций, чтобы деньги не «потерялись» при сбое). Для построения сложных отчётов по миллионам проводок и расчёта рисков идеально подходят колоночные базы, так как они сжимают данные и молниеносно выполняют агрегацию (суммирование, поиск средних значений).

1.2. Лендинги проектов и CRM-система

• **Рекомендуемый тип СУБД:** Документоориентированная (NoSQL) СУБД для лендингов (например, MongoDB) и Реляционная СУБД для CRM (например, PostgreSQL). \
• **Почему:** Каждый жилой комплекс или бизнес-центр имеет свои уникальные характеристики (этажность, планировки, акции, разные поля в формах захвата). Документная база хранит данные в формате JSON, что позволяет мгновенно менять структуру карточки проекта без правки таблиц. Для CRM же важны строгие связи между клиентом, менеджером, сделкой и объектом недвижимости, поэтому там надёжнее классический SQL.

1.3. База знаний отдела контроля качества (нормы, правила, обучение)

• **Рекомендуемый тип СУБД:** Иерархическая или Документоориентированная СУБД (например, MongoDB или специализированные движки вроде Elasticsearch для полнотекстового поиска по регламентам). \
• **Почему:** Структура компании, регламенты и СНиПы имеют древовидную вложенность (Департамент -> Отдел -> Должность -> Инструкция -> Чек-лист). В документной базе такую иерархию удобно хранить в виде вложенных JSON-документов без создания десятков промежуточных таблиц.

1.4. Логистика: маршруты доставки материалов и распределение курьеров

• **Рекомендуемый тип СУБД:** Графовая СУБД (например, Neo4j или ArangoDB). \
• **Почему:** Дорожная сеть, склады, строительные площадки, пробки и курьеры — это классический граф (вершины — точки доставки и курьеры, рёбра — дороги, время в пути и стоимость). В реляционных базах поиск кратчайшего пути или пересчёт маршрута при поломке машины требует тяжёлых рекурсивных запросов (JOIN), которые работают медленно. Графовая СУБД хранит связи физически как указатели, поэтому находит оптимальные маршруты за миллисекунды.

## Задание 2. Транзакции

Для успешного пополнения баланса телефона транзакция должна пройти через шесть основных шагов, которые обеспечивают целостность данных и защиту от потери или дублирования денег (принципы ACID).

**Пошаговый процесс транзакции**

• **Шаг 1.** *Инициализация и проверка входных данных.* Система принимает запрос от пользователя (номер телефона, сумма, платёжный метод) и проверяет валидность данных, лимиты и существование абонента в базе оператора. \
• **Шаг 2.** *Открытие транзакции и резервирование средств (Холдирование).* Банк или платёжный шлюз открывает транзакцию (BEGIN TRANSACTION), проверяет баланс карты отправителя и замораживает нужную сумму, чтобы пользователь не мог потратить эти же деньги параллельно в другом месте. \
• **Шаг 3.** *Списание средств со счёта отправителя.* Платёжная система уменьшает баланс счёта плательщика на сумму пополнения и фиксирует эту операцию в журнале транзакций (Write-Ahead Log). \
• **Шаг 4.** *Передача запроса и зачисление на баланс оператора.* Платёжный шлюз отправляет подтверждение оператору связи, после чего биллинговая система оператора увеличивает баланс лицевого счёта абонента на соответствующую сумму. \
• **Шаг 5.** *Фиксация транзакции (Commit).* Получив подтверждение об успешном зачислении от оператора связи, система выполняет команду COMMIT — окончательно списывает замороженные средства у отправителя и делает изменения постоянными в обеих базах данных. (Если на шаге 4 произошёл сбой, выполняется ROLLBACK, и замороженные деньги возвращаются пользователю). \
• **Шаг 6.** *Формирование чека и уведомление пользователя.* Система присваивает операции финальный статус «Успешно», формирует фискальный чек и отправляет SMS или push-уведомление абоненту о зачислении средств. 

## Задание 3. SQL vs NoSQL

Реляционные базы данных (SQL) превосходят нереляционные (NoSQL) в задачах, где критически важны строгий порядок, точность расчётов и сложные взаимосвязи между данными.

**Пять главных преимуществ SQL-систем**

• *Гарантия целостности данных (ACID).* SQL-базы строго соблюдают принципы атомарности, согласованности, изолированности и долговечности транзакций. Это защищает систему от потери или искажения информации при сбоях, что незаменимо в банковской сфере и бухгалтерии. \
• *Чёткая структура и валидация на уровне схемы.* Заранее заданная табличная схема с жёсткой типизацией и внешними ключами (FOREIGN KEY) не позволяет записать в базу некорректные или неполные данные. Разработчикам не нужно писать дополнительный код для проверки базовой структуры каждой записи. \
• *Стандартизированный и мощный язык запросов.* Язык SQL является единым мировым стандартом для всех реляционных СУБД. Он позволяет выполнять сложные выборки, фильтрацию и многоуровневую аналитику без глубокого переписывания кода при смене движка базы данных. \
• *Эффективная работа со сложными связями (JOIN).* Реляционная модель изначально спроектирована для объединения данных из множества разных таблиц. Благодаря нормализации данные не дублируются, что экономит место на диске и исключает расхождения при обновлении информации. \
• *Зрелая экосистема и предсказуемость.* SQL-системы развиваются десятилетиями, поэтому для них существует огромное количество готовых инструментов для резервного копирования, мониторинга и аналитики. Кроме того, на рынке гораздо проще найти опытных специалистов по реляционным базам данных.

## Задание 4. Кластеры

При работе с кластером из 1000 машин и огромными объёмами данных на первый план выходит умение системы работать в условиях неизбежных аппаратных сбоев и сетевых задержек.

1. На основе какого критерия выбирать тип СУБД?

Главным теоретическим фундаментом для выбора здесь является CAP-теорема (теорема Брюера). Она гласит, что в любой распределённой системе при возникновении разделения сети (P — Partition Tolerance) приходится выбирать между строгой согласованностью данных (C — Consistency) и их постоянной доступностью (A — Availability). \
• Почему выбор падает на AP-системы (или гибридные с Eventual Consistency): На кластере из 1000 серверов выход из строя дисков, сетевых карт или отдельных узлов — это не форс-мажор, а ежедневная рутина. Поэтому устойчивость к разделению сети (P) обязательна. \
• Практический критерий выбора — горизонтальная масштабируемость (Horizontal Scaling) и шардирование (Sharding): Классические монолитные SQL-базы плохо масштабируются на 1000 узлов из-за накладных расходов на распределённые блокировки и транзакции. Поэтому выбирать нужно распределённые NoSQL или NewSQL / колоночные MPP-системы (например, Apache Cassandra, HBase, ClickHouse или распределённые хранилища вроде HDFS / S3), которые умеют автоматически делить данные на части (шарды) и раскладывать их по всем 1000 машинам с репликацией. \

2. Какая модель распределённых вычислений справится лучше всего и почему?

Для такого масштаба лучше всего подходят модели MapReduce и её современная эволюция — DAG (Directed Acyclic Graph — направленный ациклический граф) с вычислениями в оперативной памяти (In-Memory), реализованная в Apache Spark.

Почему именно эта модель (и конкретно Apache Spark) является оптимальной:

• Принцип локальности данных (Data Locality). Вместо того чтобы перекачивать петабайты данных по сети на один мощный вычислительный сервер (что «положит» сеть), модель отправляет код вычислений на те узлы, где уже лежат нужные куски данных. Каждая из 1000 машин обрабатывает свою локальную часть информации. \
• Высокая отказоустойчивость (Fault Tolerance). Если во время многочасового расчёта 5 из 1000 машин сгорят или перезагрузятся, система не упадёт. Благодаря графу зависимостей (RDD / DAG в Spark) или перезапуску задач (в MapReduce) кластер автоматически пересчитает только потерянные фрагменты данных на здоровых узлах. \
• Скорость обработки в памяти (преимущество DAG/Spark перед классическим MapReduce). Классический Hadoop MapReduce после каждого шага сбрасывает промежуточные результаты на жёсткий диск, что замедляет работу. Модель DAG (в Apache Spark) строит оптимальный план выполнения и держит промежуточные данные в оперативной памяти (RAM) всех 1000 серверов, ускоряя вычисления в десятки и сотни раз. \
• Линейное масштабирование. Модель позволяет распараллелить задачу практически без потерь эффективности — добавление новых машин в кластер пропорционально сокращает время расчётов.

**Краткое резюме для ответа**

1. Критерий выбора СУБД: ориентация на CAP-теорему (выбор в пользу отказоустойчивости и доступности — AP с согласованностью в конечном счёте) и поддержка автоматического шардирования для равномерного распределения данных по 1000 узлам. \
2. Модель вычислений: MapReduce / In-Memory DAG (Apache Spark), так как она реализует принцип локальности данных (не гоняет терабайты по сети), автоматически восстанавливается при сбоях отдельных серверов и эффективно использует оперативную память всего кластера. \
